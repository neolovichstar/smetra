# Коммуникация, подписки и конвейер автоматизации «Сметры»

## Принципы

1. Сервер, а не браузер, принимает решение о доступе к функции и состоянии платежа.
2. ИИ извлекает намерение и сущности; стоимость определяет детерминированный денежный движок.
3. Любая запись с финансовым, клиентским или внешним эффектом проходит через проверяемое подтверждение.
4. Доступ к переписке определяется членством в конкретном разговоре. Администратор видит служебную очередь и агрегаты, но не получает универсальный просмотр частных смет и личных чатов.
5. Сайт и Android должны работать через один прикладной API и одну схему пользователя. Подписанные внешние callbacks проверяются на сервере и идемпотентно применяются.

Ключи доступа: quotes.unlimited, ads.disable, assistant.priority, export.pdf.clean, export.xlsx, storage.bytes, finance.manage, quote.branding, workspace.team, realtime.collaboration. В продукте следует использовать идентификаторы тарифов, а не сравнивать отображаемые названия тарифов.

Подписка — это подтверждённая запись billing_subscriptions с product_code, provider, status и интервалом действия. URL возврата из платёжной формы не выдаёт права. Единственная точка активации — подтверждённый webhook/проверка провайдера с защитой от повторной обработки. Снижение тарифа не удаляет рабочие данные: новые операции, превышающие лимит, временно блокируются, загрузка/экспорт пользовательских данных сохраняются согласно правилам тарифа и политике хранения.

### Rewarded Video

Создание попытки просмотра и получение credits должны быть двумя этапами. Сервер создаёт одноразовый attempt_id; callback проверяется по официальному механизму верификации/подписи Яндекса и по тому же attempt_id; уникальное ограничение исключает повторное начисление. Только подтверждённый callback завершает попытку и атомарно записывает +3 токена в ledger. Клиентский сигнал «ролик досмотрен» не является доказательством. Интеграцию нельзя включать в production, пока не проверены конкретный формат callback/подписи, тестовый слот и фактическая доставка callback.

## Коммуникационная модель

В приватной схеме БД используются chat_conversations, chat_members и chat_messages. Разговор содержит kind, quote_id, project_id, workspace_id, status и очередь эскалации. Сообщение не считается доступным только потому, что его UUID известен: API проверяет членство, а обновление/удаление участников проверяется отдельно.

- Личный чат: два участника и уникальный direct_key из пары ID.
- Обсуждение сметы: quote_id, автор и подтверждённый аккаунт клиента. Публикуемая/утверждаемая версия сметы остаётся в собственной системе версий; чат ссылается на смету, а не копирует сумму в отдельный источник правды.
- Объектный чат: workspace_id/project_id. Создавать его можно только участнику активного TEAM-пространства; начальный список участников набирается из workspace_members.
- Сообщество: открытые категории general, finishing, electrical, plumbing, subcontract. Это отдельные публичные каналы, не связанные с CRM-клиентами или частными чатами.
- Поддержка: отдельный ticket/conversation на каждое обращение, история сообщений сохраняется; статус needs_human создаёт запись в администраторской очереди.

ID профиля — публичный адрес для точного поиска и начала переписки. Он никогда не является bearer-токеном и не даёт права читать историю пользователя. В каталоге не показываются почта, телефон или private metadata.

Текущий клиентский прототип обновляет сообщения коротким polling через прикладной API. Это безопасная промежуточная доставка для существующей системы собственной сессионной авторизации. Для настоящего Supabase Realtime нужен отдельный проверенный мост удостоверения пользователя в Realtime JWT/Policies или серверная авторизация приватных каналов. Нельзя класть service_role ключ в браузер, открывать таблицы anon и считать случайный channel UUID авторизацией.

## Чат бесплатной поддержки

Системные инструкции ассистента должны содержать версионируемую базу знаний о текущей версии сайта и Android, способах входа, тарифах, сметах, клиентах, объектах, файлах, оплатах и известных ограничениях. Перед ответом ему передаётся минимальный контекст текущего аккаунта и релевантная переписка, но не пароли, платежные секреты или произвольная история чужих пользователей. Для изменений инфраструктуры и индивидуального платежного статуса ответ требует актуального API-источника.

Если пользователь прямо просит человека, ответ не подтверждается моделью либо провайдер недоступен/возвращает неправильный формат — сообщение сохраняется, needs_human включается, причина логируется, счётчик очереди меняется. Админка опрашивает очередь; push-доставка может подключаться через существующий push_outbox только с реальной проверкой устройства/доставки. ИИ поддержки бесплатен для пользователя, но его стоимость всё равно учитывается в внутренней экономике.

## ИИ-парсинг и структура JSON

Аудио идёт в серверный upload endpoint с ограничениями размера/длительности и одноразовым job_id. Whisper транскрибирует его; лёгкая модель извлекает структуру, но не формирует окончательные денежные итоги. Нормализованный hash и версия prompt/schema используются в Redis-кэше. В кэш не помещаются частные документы без разграничения tenant/workspace и явного срока жизни.

Пример нормализованного контракта:

Количество передаётся как десятичная строка, деньги — целые копейки. Отсутствующие цены остаются null; модель не должна выдумывать цену. Расчётный движок сверяет schema_version, единицы, диапазоны и ссылки каталога, потом рассчитывает налоги/скидки/коэффициенты без floating-point денег, сохраняет новую версию сметы в транзакции и формирует аудит.

## Конвейер «в один клик»

1. Голос/файл: браузер или Android отправляет аудио в API Vercel; сервер ограничивает тип, размер, длительность и частоту запросов.
2. Транскрибация: очередь/задача вызывает Whisper через OpenRouter, сохраняет статус job и транскрипт с ограниченным доступом.
3. Нормализация: DeepSeek-Chat извлекает JSON по версии схемы; Upstash Redis проверяется по hash нормализованного текста + языка + модели + schema/prompt version. Cache miss не должен ломать запрос.
4. Математика: жёсткий движок сверяет каталог и рассчитывает сумму. Финансовый сервис считает полученные авансы минус расходы/обязательства по объекту. Если подтверждённая закупка превышает доступный аванс, транзакция создаёт idempotent push_outbox событие директору.
5. Клиентское согласование: для опубликованной версии включаются/выключаются необязательные строки; сервер пересчитывает итог, сохраняет выбранные опции, неизменяемую утверждаемую версию, actor/time/terms и аудит. Цена на фронтенде — только preview.
6. Документы и закупки: шаблон договора генерирует PDF по утверждённой версии и сохраняет контрольный hash документа. Картинка печати — визуальный реквизит, а не криптографическая цифровая подпись. Юридически значимая ЭП требует применимого провайдера/сертификата и проверяемого подписания.
7. Заказ поставщику: формируется спецификация с product IDs, количествами, единицами, адресом доставки и idempotency key. Создание реального заказа делается только через подтверждённый контракт API/партнёрскую программу и отдельное подтверждение цены/доставки. Комиссия 3% — гипотеза модели до договорённости и фактических выплат ритейлера.

## Ассистент с инструментами и подтверждениями

Каждый tool имеет схему аргументов и серверную проверку пользователя/workspace. Безопасные чтения доступны сразу. create_quote_draft создаёт черновик в выбранном пользователем профиле. update_quote_items, publish_quote, send_to_client, create_purchase, record_expense и create_contract сначала записывают proposal/pending action с кратким предпросмотром: что изменится, для кого, итоговая сумма, получатель и версия исходных данных. Кнопки «Подтвердить» и «Отмена» показываются рядом с композером. Подтверждение связано с user_id, workspace_id, action hash, revision и коротким сроком жизни; повторный вызов не выполняет действие дважды. Отправка клиенту, расходование денег, закупка и публикация юридического документа не выполняются тихо.

## Администраторская аналитика

Панель показывает только необходимые агрегаты: активные аккаунты, DAU/MAU по зарегистрированным событиям, подтверждённые платежи минус проведённые возвраты, платёжную воронку, количество смет/проектов/клиентов/файлов, состояние поддержки, очереди фоновых задач, ошибки провайдеров и бюджет ИИ. «Сейчас онлайн» вычисляется из свежего heartbeat и не подменяется сроком действия cookie. Любое администраторское действие имеет audit record; содержание личной переписки и клиентских документов не включается в общую сводку.

## Масштабирование и экономика

300 000 MAU сами по себе не доказывают возможность выдержать «гигантский DAU»: нужны профиль трафика, peak requests/s, доля голосовых задач, длина диалога, файловый объём, число concurrent connections и latency внешних поставщиков. Статика кэшируется CDN; прикладной API — без состояния; фоновые AI/PDF/exports — идемпотентные jobs с повторами; Upstash служит краткоживущим кэшем/лимитером, PostgreSQL остаётся источником истины. Pool/connection limits должны учитывать сумму всех тёплых serverless-инстансов, а не только один процесс.

Пример только для токенной составляющей, если эффективная цена действительно равна 0,14 USD / 1 млн токенов: при 4 000 токенах суммарного input+output одна задача ≈ 0,00056 USD; 100 000 таких задач ≈ 56 USD. В это не входят транскрибация аудио, retries, PDF, БД, Redis, сеть, push и комиссии. Стоимость/пользователь должна считаться из фактических usage metrics, а не из прайсинга в prompt.

Критерии нагрузочного допуска: воспроизводимый k6/Locust сценарий, постепенное масштабирование, peak 2–3× целевой прогноз, измеренный p50/p95/p99, отсутствие межтенантных утечек, дублей платёжных webhook, переполнения очередей, исчерпания DB connections и неконтролируемого роста стоимости. Без этих результатов нельзя честно объявить 300k MAU доказанно проверенными.

## Производственный rollout

Схема общения аддитивна и закрыта от browser/public database ролей. Сначала миграция и unit/API/security tests на отдельной ветке, затем preview deployment и smoke tests двух аккаунтов, сценария эскалации и админ-панели; только потом release. Внешние платежные/рекламные/ритейл-API и сертификаты не объявляются включёнными, пока тестовые и боевые callbacks не подтвердились реальными ответами провайдера.
