# Construction Intelligence — архитектурные этапы

Дата: 2026-10-24. Решение для продукта «сметра.»; фиксирует контракты до подключения платных прав. Никакие функции, описанные в будущих этапах, не считаются выпущенными до реализации API, тестов и релиза.

## 1. График работ (PRO Плюс / TEAM, после реализации планов)

**Первый работающий этап:** \`apps/web/schedule-planner.js\` — локальный предварительный график по выбранной смете; календарь Пн–Пт/каждый день, последовательные работы, задаваемые пользователем паузы, предупреждения при неизвестных нормах, без записи на сервер.

Последующее серверное проектирование:

- \`project_schedule_versions(id, workspace_id, project_id, quote_revision, version, status, start_on, workday_pattern, created_by, created_at)\`
- \`project_schedule_tasks(id, version_id, source_quote_item_id, stage, description, quantity, unit, productivity, duration_workdays, starts_on, ends_on, status, assignee_id)\`
- \`schedule_dependencies(version_id, predecessor_task_id, successor_task_id, type, lag_calendar_days)\`
- \`schedule_events(id, workspace_id, version_id, actor_id, event, payload, created_at)\`

**Точные правила:** API запрашивает фактические смены, размер бригады, норматив производителя материала, измерения влажности и разрешённые выходные. До ввода данных план является предварительным. LLM может предложить структуру, но не утверждает окончательную дату; критический путь и пересчёт производит детерминированный бэкенд. Все изменения версии графика журналируются, пуши отправляются только после явной публикации плана, в соответствии с настройками уведомлений. Доступ к графику клиента — через авторизованный ограниченный viewer, а не публичный список участников.

## 2. Склад остатков (PRO Плюс)

**Никакого складского учёта через локальные значения браузера:** данные должны быть консистентны между устройствами и членами команды.

Предлагаемые сущности:
- \`warehouse_locations(id, workspace_id, name, owner_id)\`
- \`material_lots(id, workspace_id, location_id, catalog_item_id, material_name, normalized_unit, batch, expires_on, created_at)\`
- \`stock_movements(id, workspace_id, lot_id, kind, quantity_decimal, project_id, quote_id, occurred_at, actor_id, idempotency_key)\`
- \`stock_reservations(id, workspace_id, lot_id, project_id, quantity_decimal, status, created_by, version)\`

**Инварианты:** количество сохраняется как Decimal в канонической единице, отрицательные движения запрещены; свободный остаток = приход − расход − активные резервы. Резерв и списание выполняются атомарно в транзакции с блокировкой партии, а повтор с тем же idempotency key не уменьшает остатки второй раз. Только роли workspace с разрешением на запись могут менять остатки. \`workspace_id\` проверяется на каждом уровне (RLS/сервер), входные идентификаторы клиента не доверенные.

**Сопоставление смет:** совпадение по каталожному ID, размерности единицы и затем нормализованному имени с ручным подтверждением. «Мешок 25 кг» не равен «мешку 30 кг»; объём/вес не переводится без известной плотности или коэффициента. Остатки и экономия показываются только из подтверждённых движений и реальных цен; не списывать материалы из-за одного совета ИИ.

**UX:** снабженец видит склад → предлагает использовать остаток в новом проекте → пользователь подтверждает резерв → после фактической передачи фиксируется расход → при возврате фиксируется приход.

## 3. Панорамы и 3D-тур (TEAM)

Сначала **360°-фото**: запись панорамы equirectangular в отдельный защищённый storage bucket, идентификаторы \`workspace_id/object_id/zone_id\`, ограниченный по времени signed read URL, лимит размера и MIME/сигнатуры, удаление EXIF/GPS, фоновое построение thumbnail и multi-resolution tiles. WebGL/browser-viewer подгружается по требованию с учётом устройств низкой мощности. Переход между комнатами — подтверждённые пользователем hotspots; это тур между 360° точками, **не свободное перемещение в 3D**.

Затем — мультивидовой 3DGS/NeRF: сбор видеокадров с **изменением позиции камеры**, sufficient parallax, COLMAP / camera pose estimation, проверка качества входа, GPU-очередь обработки и экспорт .ply/splat. На телефоне — просмотр адаптивных уровней детализации, а не обучение крупной сцены. Если восстановление не прошло, пользователь получает исходное панорамное фото, а не выдуманный 3D.

Предлагаемые сущности:
- \`site_captures(id, workspace_id, object_id, zone_id, kind, status, storage_path, taken_at, created_by)\`
- \`capture_jobs(id, capture_id, model_version, status, progress, error_code, gpu_seconds, created_at)\`
- \`capture_tour_links(id, workspace_id, from_capture_id, to_capture_id, orientation, position)\`

**Безопасность:** медиа объекта может содержать личные данные жильцов; просмотр разрешён только явно приглашённому клиенту и команде конкретного объекта. Запрет публичной индексации, короткие signed URLs, ограничения объёма и числа GPU-job на workspace, возможность полного удаления исходников/моделей и retention policy. Никогда не выдавать панораму одной комнаты за точную метрическую 3D-модель.

## Entitlements перед продажей

На момент проектирования активная ветка продукта различает основные планы \`free\` и \`pro\`; отдельные серверные entitlements для \`pro_plus\` и \`team\` не подтверждены. Нельзя добавлять «TEAM за 3 990 ₽» только текстом в UI. Сперва ввести серверный каталог тарифов и единый \`can(user, workspace, capability)\` с управлением ролями, квотами, платежами и тестами 403. После этого: \`schedule_advanced\` → PRO Плюс/TEAM, \`inventory\` → PRO Плюс/TEAM, \`site_tours\` и GPU квоты → TEAM.

## Границы первого выпуска

Планировщик является read-only предпросмотром. Он не предоставляет юридической гарантии срока ремонта, не отправляет пуши и не меняет сметы. Склад и туры **не выпущены**, пока не появятся защищённая серверная модель, подтверждение прав доступа, фоновые задачи и тесты отказоустойчивости.
