# Восстановление PostgreSQL «сметры.»

Приложение использует приватную схему `smetra` в Supabase PostgreSQL. Здесь рассматривается **логическая копия прикладной схемы**, а не всего проекта Supabase.

## Обязательные требования перед продакшеном

1. Проверить наличие резервных копий в тарифе Supabase. На Free **нельзя рассчитывать на автоматическое ежедневное восстановление**: проверенные копии следует хранить вне проекта и аккаунта БД.
2. Запускать `backup` на доверенном исполнителе с клиентскими программами **PostgreSQL 17** и нужными правами. Не держать процесс в обычном короткоживущем запросе Vercel. Не публиковать адреса подключения, пароли и архивы в Git.
3. Шифровать **оба** файла `.dump` и `.dump.json` перед загрузкой в отдельное приватное хранилище. Настроить сроки хранения, учёт успешных копий и оповещение, если свежей корректной копии нет.
4. Регулярно проверять восстановление в **новой изолированной БД**. Успешное создание архива само по себе ничего не гарантирует.
5. Отдельно защищать реальные файлы Supabase Storage, настройки Auth, роли, OAuth, конфигурацию приложения и другие внешние данные.

## Команды для доверенной машины

`DATABASE_URL` передавать через защищённое окружение, **не помещать в историю команд**. В `RESTORE_DATABASE_URL` никогда не указывать рабочую базу.

```sh
python -m backend.manage check
python -m backend.manage backup --output /private/backups/smetra-UTC-timestamp.dump

# Сначала создать пустую локальную smetra_restore_drill и подготовить роли.
RESTORE_DATABASE_URL='postgresql://localhost/smetra_restore_drill' \
  python -m backend.manage restore-check \
  --archive /private/backups/smetra-UTC-timestamp.dump
```

`backup` не перезаписывает существующие файлы. Для согласованности используется снимок PostgreSQL и `pg_dump --format=custom`. Манифест содержит SHA-256, отпечатки строк и структуры. `restore-check` проверяет содержимое строк, ограничения, индексы, разрешения и RLS.

Восстановление разрешено **только на loopback**, только в БД вида `smetra_restore_*`, и только если схема `smetra` в ней отсутствует.

## Порядок действий при аварии

- Подготовить совместимую PostgreSQL, платформенные схемы и требуемые роли. `pg_restore --no-owner` **не создаёт** отсутствующие роли для GRANT.
- Восстановить данные и проверить права доступа, изоляцию пользователей, индексы, целостность и версии миграций.
- Сопоставить состояние платежей с ЮKassa; **до сверки не запускать** обработчики платежей и почтовых уведомлений.
- Проверить наличие объектов хранилища и внешних интеграций, только затем переключать рабочий сервис.

## Что отслеживать

- Время последнего успешного **внешнего зашифрованного** архива.
- Дату последней **успешной проверки восстановления**, число таблиц и контрольные суммы.
- Допустимую потерю данных (RPO), измеренное время восстановления (RTO) и доступность ключей.
- Наличие файлов из объектного хранилища и независимой истории платёжного провайдера.

Проверки CI подтверждают совместимость тестового восстановления. **Они не являются доказательством наличия резервной копии реальной базы.**
