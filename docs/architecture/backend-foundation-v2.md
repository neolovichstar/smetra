# Сметра: фундамент backend v2 (архитектурное решение)

Статус: проект архитектуры для реализации; **не является кодом или применённой миграцией**.  
Дата ревизии: 24 октября 2026.  
Исходная ветка: feat/ecosystem-release-20261024, commit 2c9db1be37d70109fbf6968b2d48cb5703a4087c.

## 1. Результат аудита существующей системы

Продукт уже имеет полноценные серверные сущности. Нельзя начинать новую экосистему созданием параллельных таблиц «estimates», «profiles» или дублированием платежей.

| Ответственность | Уже существует | Целевое развитие |
| --- | --- | --- |
| Идентичность | users, user_profiles, sessions, external_identities | Проверенная личность и получатель приглашений; не менять текущие ID |
| Командная работа | workspaces, workspace_members | Роли, назначения, membership authorization |
| Сметы | quotes, quote_items | Существующий API остается; новые сценарии используют его |
| Публикации | quote_versions, published_version | Неизменяемый контракт версии для получателя |
| Согласование | public_token, approval_state, comments, activity | Персональные передачи и протокол утверждения |
| Тарифы | plan_catalog, entitlements, billing_subscriptions, billing_intents | Единый каталог прав и единые лимиты по workspace |
| Уведомления | notifications, push_outbox, push_devices | Надежная бизнес-событийная шина и доставка |
| Задания | assistant_jobs, file processing | Общий долговечный реестр разных типов заданий |
| Аналитика/квоты | events, ai_usage, рекламные кредиты | Разделение бизнес-событий, финансовой аналитики и разрешений |

В Supabase используется схема smetra, у существующих бизнес-таблиц включен RLS; прикладная роль — smetra_runtime. Это **не** стандартная модель, в которой любой JWT автоматически соответствует auth.uid() Supabase. Авторизация и границы доступа должны учитывать собственные сессии приложения и текущую модель сметры.

Найдены важные технические свойства:
- quote_items.data хранит структурированную строку в сериализованном виде; при редактировании физические записи quote_items удаляются и создаются заново. Поэтому опираться на физический quote_items.id при клиентском согласовании нельзя. Стабильная идентичность строк — line_id внутри снимка версии.
- quote_versions идентифицируется парой (quote_id, version), а не отдельным универсальным UUID.
- Публикация уже создает снимок; расчеты и защита подтвержденной сметы частично реализованы.
- Публичная ссылка сейчас использует quotes.public_token. По этой ссылке можно не только читать, но и отправлять ответ, используя введенное имя. Это совместимость с действующим сценарием, **не** надежная идентификация клиента.
- Ограничение 10 бесплатных смет сейчас опирается на события quote_created владельца. Целевая модель должна учитывать начисления/расходование квоты идемпотентно и в пределах нужного workspace.
- Сохраняется возможность работы старых клиентов RuStore и старых публичных ссылок на время миграции.

Четыре read-only проверки целостности production не обнаружили отсутствующих workspace у смет, отсутствующих опубликованных snapshots, отсутствующего membership владельцев или осиротевших строк quote_items. Это только точечная предварительная проверка, не полный аудит безопасности.

## 2. Архитектурные решения

**ADR-01 — Каноническая смета остается quotes.**
Публичное слово «смета» не требует переименования таблицы. Применение нового API или маппера допустимо, но никакого двойного источника истины.

**ADR-02 — Snapshot неизменяем.**
Один опубликованный номер версии соответствует одному неизменяемому содержимому, валюте, составу строк и расчетной сумме. Любая последующая корректировка создает новую версию.

**ADR-03 — Клиент не редактирует quote_items.**
Действия по необязательным позициям формируют proposal для определенной версии. Состояние предложения отдельно от состояния исходной сметы.

**ADR-04 — Подтверждается определенная сумма определенной версии.**
Утверждение фиксирует actor, share, quote_id, quote_version, hash снимка, итог в минимальных единицах валюты, время и ключ идемпотентности. Изменившаяся версия отвергается конфликтом.

**ADR-05 — Один workspace — один контур бизнес-доступа.**
Права рассчитываются из server-side membership + scope ресурса + возможностей тарифного плана. Владение ссылкой не превращает клиента в участника workspace.

**ADR-06 — PostgreSQL является источником истины.**
Кэш, Realtime и очереди не хранят единственную копию бизнес-события или утверждения. События для доставки фиксируются в общей транзакции с бизнес-состоянием.

**ADR-07 — Совместимость по умолчанию.**
Работающие маршруты, публичные версии, оплаченные тарифы, Android RuStore и устаревшие идентификаторы остаются работоспособными. Все изменения включаются флагами по workspace и этапам.

## 3. Новые логические сущности: контракты

### estimate_shares

Одна запись = передача **конкретного** опубликованного снимка конкретному получателю.

Обязательные атрибуты: id, workspace_id, quote_id, quote_version, sender_user_id, recipient_user_id (nullable), recipient_email_normalized_encrypted либо отдельно защищенный email, recipient_email_hash для поиска, token_hash (unique), recipient_verification_state, permission (view/respond), status (pending/active/revoked/expired), expires_at, created_at, opened_at, responded_at, revoked_at, idempotency_key, audit metadata.

Ограничения: FK на quotes, FK по (quote_id, quote_version) на quote_versions, workspace совпадает с workspace сметы. При изменении статуса не удалять журнал. Секрет ссылки хранится только в виде хеша; сырой токен нельзя возвращать повторно или логировать.

Не допускать поиска наличия пользовательского аккаунта через публичный ответ API. Проверять владение email до создания постоянного recipient_user_id. Клиент может видеть только переданный snapshot и явно разрешенные файлы.

### estimate_proposals

Одна запись = предложение получателя по одному share и одной опубликованной версии.

Атрибуты: id, workspace_id, share_id, quote_id, quote_version, base_snapshot_hash, actor_id/verified recipient, state (draft/submitted/accepted/rejected/superseded), calculated_total_minor, calculation_version, created_at, submitted_at, decided_at, revision и idempotency_key.

Здесь нельзя записывать «исправленную сумму» из браузера. proposed total формирует backend на основе snapshot + включённых необязательных строк.

### proposal_items

Ключ: proposal_id + стабильный line_id **из опубликованного snapshot**, а не физический row id quote_items.

Атрибуты: original_line_id, chosen_included, reason, created_at. Валидатор разрешает изменение только у optional=true и запрещает изменение цены, количества, налога и названия.

### approval_events и approvals

append-only журнал: id, workspace_id, quote_id, quote_version, share_id, proposal_id (nullable), actor identity, action, before/after state, snapshot_hash, approved_total_minor, currency, idempotency_key, timestamp, technical request ID. Персональные данные сокращать до минимально необходимого объема.

Отдельная единственная действующая запись утверждения на опубликованный snapshot + share может ссылаться на журнал. Не смешивать утверждение, оплату и завершение работ.

### outbox_events

Атрибуты: id, workspace_id, aggregate_type, aggregate_id, event_type, event_version, payload_reference/safe payload, idempotency_key, recipient_scope, status (pending/leased/delivered/dead_letter), attempts, next_attempt_at, lease_until, created_at, delivered_at, last_error_code.

В outbox кладутся события внутри той же транзакции, что и business mutation. Публикация в push, Realtime, Resend и webhook выполняется **после commit**. Получатели дедуплицируют event id; ретраи экспоненциальные; dead-letter не удаляется автоматически.

### calculation_runs

Атрибуты: id, quote_id, quote_version/proposal_id, input_hash, formula_version, rounding_policy_version, currency, subtotal_minor, taxes_minor, discount_minor, total_minor, warnings, created_at, status. Для равных входных данных и версии алгоритма результат детерминирован. Денежные итоги из LLM игнорируются.

### quota_ledger

Атрибуты: id, workspace_id, actor_id, feature, unit, delta, source_type/source_id, idempotency_key, expires_at, created_at. Создание сметы и расход квоты должны происходить одной транзакцией. Отдельно учитывать начальные 10 бесплатных смет и рекламные разрешения; использовать прежние данные для backfill и reconciliation, без автоматической выдачи повторных бонусов.

## 4. Жизненный цикл

### Публикация

Действующий quotes.publish сохраняет quote_versions. Новое действие «отправить клиенту» создает share, привязанный к версии, и событие «estimate.share.created» в одной транзакции. Отправка email или push не должна открывать вторую транзакцию, способную привести к рассинхронизации.

### Просмотр

Получатель идентифицируется валидной сессией либо безопасным временным приглашением с подтверждением email. Проверяются состояние share, срок, разрешенная версия и назначение получателя. Система возвращает **read-only snapshot**. Сторонние внутренние данные (cost price, markup, других клиентов, вложения не для публикации) недоступны.

### Изменение необязательных позиций

По share и версии пользователь выбирает included=true/false только для optional=true. Сервер берет исходные строки из snapshot и вычисляет все суммы. Конкурентный draft проверяется по revision/ETag. Изменения не пишутся в quotes и quote_items.

### Утверждение

Сервер повторно авторизует actor и share, проверяет срок, актуальность версии, hash snapshot, сохраненную предлагаемую конфигурацию и пересчитывает итог. В одной транзакции записываются approval, event и outbox. Повтор того же idempotency key возвращает прежний результат; утверждение другой версии — conflict. Утвержденная версия не меняется задним числом.

### Сохранение совместимости

Старые /api/public/quote и публичные ссылки сначала остаются доступными для просмотра. Новые клиентские операции получают отдельные защищенные маршруты. Переход от анонимного approve по public_token — отдельный release gate после клиентской миграции; не отключать его мгновенно без учёта актуальных отправленных предложений.

## 5. Авторизация и доступ

Внутренний user: подтвержденная сессия приложения; проверенное членство workspace; role permissions на ресурс. Клиент-получатель: независимое share-grant, не workspace membership. Сервисный обработчик: только привилегии минимально необходимого tenant scope и проверенная подпись задания. В PostgreSQL придерживаться существующей схемы smetra_runtime, не предполагать поддержку Supabase auth.uid() без реальной идентификационной интеграции.

Нужны тесты на cross-workspace запросы, пересылку чужой ссылки, истекший и отозванный share, подмененный quote_version, украденный idempotency key, повторный webhook, параллельное утверждение и обновление назначений сотрудников.

## 6. Роллаут, данные и обратная совместимость

Фаза 0: запретить разрушительные миграции; подготовить backup/restore, базовые метрики и feature flags.

Фаза 1: **только добавочные** таблицы/индексы/политики; без удаления quotes, public_token, старых статусов. Проверка миграций в staging и restore test.

Фаза 2: новая отправка пишет immutable share и outbox. Старые отправленные сметы продолжают работать. Теневой расчёт и сравнение сумм без влияния на UI.

Фаза 3: read-only клиентский viewer; персональная авторизация; новый proposal flow. Канареечное включение на малом числе workspace.

Фаза 4: server-side approval & Realtime; double-submit и concurrency тесты; переключение только новых согласований.

Фаза 5: перенос квот и entitlement-контрактов с reconciliation старых платежей и бонусов.

Фаза 6: метрики p95, доля ошибок, расходы очередей, dead-letter и нагрузочные тесты; 1% → 10% → 50% → 100%. Откат осуществляется выключением новых маршрутов и обработчиков, а не удалением новых данных.

## 7. SLO и контрольные критерии

- Чужой workspace не читается и не изменяется даже при наличии чужого ID.
- Отправленная версия неизменяема; старые расчёты воспроизводимы.
- Необязательные пункты не влияют на исходный snapshot.
- Утверждение не принимается без доказанной связи с share.
- Повтор/параллельное подтверждение не создают дублей.
- Уведомление не отправляется до завершения транзакции и не теряется после нее.
- Истекшая и отозванная ссылка не позволяет подтвердить смету.
- Копейки, налоги, скидки и округления повторяются точно; округления фиксируются версией алгоритма.
- Действующие пользователи, оплаты и старые Android-клиенты не теряют доступа.

**Запрещено** объявлять эти критерии выполненными до автоматических тестов и ручной проверки staging/production.

## 8. Зависимости следующих пяти функций

- Голос → проверяемые draft_items → существующий расчет quotes → quote_versions.
- Обмеры → measurements с источником и точностью → формулы → draft_items.
- PDF → документ и extraction_jobs → reviewable draft_items → quote_versions.
- Email приглашение → estimate_shares + transactional outbox + доставка через Resend.
- Интерактивное согласование → proposal_items + calculation_runs + approvals + outbox.

Таким образом новые функции используют общий фундамент, а не размножают собственные механизмы прав, расчетов, уведомлений и документов.
