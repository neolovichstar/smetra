# Модель угроз «сметра.» — 30 сентября 2026

Область: веб, нативный Android, Python API на Vercel, PostgreSQL/Supabase, YooKassa, российские OAuth-провайдеры и OpenRouter. Модель описывает состояние кода, а не сертификат безопасности. Метод — STRIDE: подмена личности (S), изменение данных (T), отрицание действий (R), раскрытие (I), отказ в обслуживании (D), повышение привилегий (E). Вероятность и ущерб: низкий/средний/высокий; это качественная оценка.

## Активы, субъекты и границы

Активы: аккаунты, сессии и OAuth-идентичности; персональные данные клиентов; сметы, заказы, финансовые записи и платежи; документы, файлы, публичные ссылки; административный доступ; ключи API, база данных, резервные копии и AI-учётные данные.

Субъекты: анонимный посетитель и бот, клиент с публичной ссылкой, зарегистрированный пользователь, участник/владелец пространства, администратор, злоумышленник с действующим аккаунтом, YooKassa, OAuth- и AI-провайдеры.

Границы доверия: браузер/Android/публичный клиент → API; API → PostgreSQL/хранилище файлов/YooKassa/OAuth/OpenRouter; CI/CD → production; администратор → backend. Ответы провайдеров, содержимое файла и JSON из БД нельзя считать доверенными лишь из-за источника.

## Угрозы и проверка

| --- | --- | --- | --- | --- | --- |
| S: кража сессии или подбор пароля | Аккаунт; cookie, bearer, login/reset | Средняя / высокий | scrypt, случайные токены, HttpOnly/Secure cookie, лимиты запросов | Подтверждённый email, MFA для админа, ротация открытых ранее ключей | Тесты login/reset, аудит конфигурации SMTP и секретов |
| S/T: поддельный OAuth callback | OAuth identity; redirect/state/PKCE | Средняя / высокий | Одноразовые state и PKCE, привязка по provider ID | Проверить реальные callback и настройки провайдеров | Sandbox E2E Яндекс/VK/Mail/OK |
| E/I: доступ к чужому workspace через ID | PII, сметы, файлы, финансы; все приватные API | Высокая / критический | Членство в workspace, серверная RBAC, scoped queries, регрессионные тесты | Выделенная DB-роль без BYPASSRLS и политика tenant context; полная матрица BOLA | Cross-tenant API-тесты + DB-тест прямого доступа |
| E/I: обход RLS привилегированной ролью API | Вся БД; API → PostgreSQL | Средняя / критический | Приватная схема, revoke для anon/authenticated, `workspace_id` в SQL | Переход API на непривилегированную роль и FORCE RLS после совместимых политик | В production-like DB проверить `current_user`, `row_security_active`, запрет чужих строк |
| I/T: утечка или подмена через публичную ссылку | Смета, документы, клиентские комментарии, intake | Средняя / высокий | Криптослучайные токены, опубликованная версия, явное `public=1` для файлов, лимиты | Срок действия/отзыв ссылок и явная клиентская область данных для всех новых сущностей | Тесты private file/expired token/tenant isolation |
| T/R: поддельное платёжное уведомление | Подписка, платежи; YooKassa webhook | Высокая / критический | Backend запрашивает статус у YooKassa, сверяет магазин/сумму, идемпотентность и транзакции | Боевой sandbox/live прогон, алерты расхождений | Тесты forged/duplicate/out-of-order + sandbox webhook |
| T/E: недоверенный AI вызывает опасный инструмент | Клиенты, сметы, финансы; OpenRouter → tools | Средняя / высокий | Backend ограничивает инструменты правами и лимитами пользователя | Независимый adversarial тест prompt injection каждого инструмента | Тесты инструментов с чужими ID и подменённым prompt |
| D: автоматические заявки и большие файлы | БД/хранилище/стоимость; public intake, upload, AI | Высокая / средний | Лимиты тела/файлов, per-IP/per-form throttle, квоты, Vercel Firewall | Мониторинг ложных блокировок, cleanup rate-limit записей, нагрузочный прогон | 413/429 и concurrency тесты, staging load test |
| I: PII/секреты в логах и бэкапах | Логи, backup, CI artifacts | Средняя / высокий | Логи не пишут query string и тела; игнорируемые локальные секреты | Ротация ранее раскрытых ключей; проверка восстановления и retention | Secret scan, просмотр логов, restore drill |
| T/E: компрометация CI/CD | Исходники, APK, production env | Средняя / критический | Раздельная сборка и подпись, ограниченные права workflow | Pin actions по SHA, защита ветки, provenance/SBOM и аудит сторонних зависимостей | Проверка настроек GitHub, reproducible/signature check |

## Блокирующие условия для заявления «production security ready»

Серверная DB-роль сейчас привилегирована и может обходить RLS. Политики для запросов от непривилегированной роли не внедрены. Секреты, когда-либо отправленные в чат, должны быть перевыпущены. Не проведены восстановление backup, независимый ASVS L2 аудит, sandbox-проверка YooKassa/OAuth и полноценный pentest. Пока эти пункты открыты, не утверждать, что защита проверена полностью.
